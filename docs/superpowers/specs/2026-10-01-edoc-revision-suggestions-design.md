# EDoc「修訂建議」功能規格

日期：26/10/01。規格版本：0.1。狀態：供檢視；尚未實作、提交或部署。

## 1. 目標與已確認決定

A、B 公司合作修改同一份文件。B 可以提出修改並留下記錄；具相應權限的人決定哪些內容採納。正式內容與版號只在「確認並發布」成功後更新。

本輪已確認：

- 功能名稱統一為「修訂建議」，不用「修改提案」「提交審閱」或上下級審批語氣。
- 分享連結時可設定權限，事後可再開啟、關閉；保留誰修改、誰採納及誰發布的記錄。
- 每項可採納或不採納；允許部分採納後發布。
- B 建議 5 項，A 採納 3 項、不採納 2 項：新版只含採納的 3 項，但另外 2 項的原建議及處理記錄完整保留。
- 本輪只整理規格，不改產品、建立雲端資源、Commit、Push 或部署。

以下以「本版建議」標示尚未由使用者逐項選定的預設；均屬待檢視的設計，不是既有功能。

## 2. 現況與變更邊界

本輪查閱的本機 Worker `/versions` 會驗證編輯連結與最新基準，直接附加正式版本並更新 latestVersion。現有正式版本唯讀，編輯發生在 Draft；具名連結目前綁定名字、文件及管理員／編輯者角色。

本功能加入正式發布前的「修訂建議」流程。保留現有差異引擎、Word 類型呈現與正式版本不可覆寫原則。既有文件、連結及所有歷史版本不能因功能上線被直接改寫或重新編號。

本版建議：以每份文件的設定啟用「修訂建議模式」，預設不自動替舊文件啟用。啟用時先指定文件主控者並映射原有連結權限；原編輯者預設只能提出建議，不能因舊 editor 身分繞過發布限制。模式切換本身留事件記錄；有未結清建議時不得靜默停用；停用確認須列出未結清項目。停用後既有建議與歷程仍可依權限查看，但不能再採納或發布這些建議；重新啟用後須先重新比較最新正式版。

## 3. 用語與基本物件

| 名稱 | 定義與顯示 |
|---|---|
| 正式版本 | v1.0、v1.1；一般公開網址與正式 PDF 採用的內容 |
| 草稿 | 尚未送出，修改者自己的編輯內容；不佔正式版號 |
| 修訂建議 | S001；顯示「修訂建議 S001・基於 v1.0」 |
| 建議項目 | S001-01 等固定識別碼，每項有修改前後內容 |
| 採納／不採納 | 對個別項目的處理結果；尚未決定顯示「待討論」 |
| 待發布內容 | 將目前選定的採納項目套用後的預覽，還不是正式版 |
| 建議記錄 | 原始內容、討論、每次決定、發布關聯的完整歷程 |

主要按鈕：「開始修訂」「送出修訂建議」「採納」「不採納」「加入說明」「預覽新版」「確認並發布」「撤回建議」。不用「核准」「駁回」「提交審閱」。權限管理可以用「可決定採納」「可發布正式版」。

關閉編輯草稿與撤回已送出的建議是不同動作。撤回只改狀態，不刪記錄。

## 4. 權限與分享

### 4.1 每人、每文件的能力

| 能力 | 可做事項 | 不包含 |
|---|---|---|
| 檢視協作內容與留言 | 查看被授權的建議、歷程，加入討論 | 提出修改、決定採納、正式發布 |
| 提出修訂建議 | 從正式版建立草稿，送出自己的建議；符合條件時撤回自己的建議 | 替他人作決定、直接更新正式版號 |
| 決定採納 | 逐項／整批採納或不採納，留下處理說明 | 自動發布正式版本 |
| 發布正式版 | 預覽已選定內容並確認正式發布 | 改寫已發布版本、代替別人作採納決定 |
| 管理本文件分享權限 | 建立、調整、停用具名連結，授權以上能力 | 無記錄地改權限或刪除歷程 |

具名分享連結由主控者設定，權限可組合；例如某人只有採納權，另一人只有發布權。主控者預設具本文件全部能力，也可授權合作方處理；不把 A／B 公司身分直接當成權限。

發布權及管理權需要協作內容檢視能力；介面自動帶入此依賴。發布者只能發布已記錄為採納的項目，不能利用預覽直接改正文。需要調整文字時，應建立新的修訂建議。

本版建議：有採納權的人可以處理自己的建議，記錄仍會呈現同一提出／處理者；第一階段不強制雙人或雙公司共同同意。將來若需要雙方同意，可另加規則，不能暗中把這次的單一採納流程當成雙方簽署。

### 4.2 分享介面與事後調整

分享面板每列顯示：顯示名稱、所屬公司（選填）、本文件權限、有效／停用狀態，以及「調整權限」「停用連結」。預設只授予檢視與提出建議；採納、發布與管理權由主控者明確開啟。

調整後由伺服器立即保存並於下一個操作請求生效；網頁已有按鈕、舊分頁或已開啟的編輯器不能繞過檢查。沒有權限的未完成草稿保留在原瀏覽器，但不能再送出或發布。待處理建議不因提出者連結停用而消失；其後能否查看，依目前檢視權限。

每次權限變更記錄操作者、目標連結識別碼、變更前後能力、伺服器時間；不得記錄連結原始 token 或密碼。

已有效作出的採納決定不因其操作者事後失去權限自動取消；主控者如要改變決定，須新增決定事件。失去發布權的人不能再發起新的發布。

### 4.3 密碼與具名身分

本版建議第一階段沿用「每人一條具名連結」，暫不新增共用密碼。原因：符合現有架構，可分別撤銷權限並記錄操作者。Word 式密碼鎖定可列為後續額外保護，不能拿同一密碼代替多人身分。

名字來自伺服器上的連結記錄，不接受客戶端自行聲稱的操作者。連結轉交後系統只能記錄「使用該具名連結的操作」，不能聲稱已驗證真人。改名不改舊事件的名字快照；若需不同成員接手，另建連結，保留原成員識別碼。

若未來加入密碼，仍須先辨識具名操作者；密碼不能自動取得原本沒有的採納／發布權。主控者變更或連結輪替也須留事件，不能失去最後一位可管理本文件的有效主控者。

## 5. 修訂建議的建立與狀態

流程：正式版 v1.0 → B 編輯草稿 → 送出 S001 → 逐項討論與處理 → 預覽採納內容 → 確認並發布 v1.1。

| 狀態 | 含義 | 正式版號 |
|---|---|---|
| 草稿 | 尚未送出，可持續編輯 | 不變 |
| 待討論 | 已送出，至少一項待決定 | 不變 |
| 待發布 | 本次預計發布範圍中的項目已作決定且含可套用的採納項目 | 不變 |
| 發布處理中 | 發布請求已受理，等待正式儲存及網站／PDF更新 | 不提前顯示成功 |
| 已完成 | 全部項目已處理；採納項目已發布，或全部不採納 | 成功發布時才增加 |
| 已撤回 | 提出者撤回尚未有項目發布的建議 | 不變 |
| 需重新比較 | 基準正式版已變動或範圍出現衝突 | 不變 |

建議狀態由項目與發布結果推導，不可由客戶端隨意宣告「已完成」。建議可以先發布已處理的部分，留下其餘待討論項目；此時建議維持待討論，顯示哪些項目已併入哪一版。

送出後原始建議內容凍結，不能改掉別人已看過或決定過的文字。若要修改建議，可「調整後再提出」產生下一份建議，關聯來源 S001，並標示被取代的範圍；不抹去 S001。第一階段每次發布處理一份建議，不自動將多人的不同建議整批混合。

草稿及送出內容都以正式版號與乾淨正文 hash 綁定。第一次送出若基準已變動，保留草稿並要求重新比較，不靜默套用到另一版。

## 6. 逐項採納與不採納

每項顯示章節、原文、建議文字、提出者、提出時間、目前決定與討論。新增／刪除／替換／格式異動均有明確範圍；同一處替換文字的「刪舊＋加新」是一個完整項目，不能只採納其中半邊。

系統給項目固定識別碼，不因排序或重新渲染變動。依現有差異引擎產生項目；不能假定「5 個建議項目」等於正式版本統計的「5 處修改」。統計依最終實際正文重算。

- 「採納」只更新該項決定與預覽，不即刻改正式版本。
- 「不採納」不把該項套入預覽；保留建議全文及決定記錄。
- 「待討論」維持未決，不得由系統視為不採納。
- 整批處理只能作用於畫面明示的範圍，篩選時不包含隱藏項目。
- 提出／處理說明是選填，不增加強制填寫摘要表單。採納／不採納與操作者、時間則必須保存。
- 決定可在發布前變更，使用新增事件表示「原不採納 → 後採納」，不覆寫前次事件。
- 語意相依或文字範圍重疊的項目，先提示並要求一起處理或重新提出，不能生成破碎句子或依序偷偷覆蓋。

已發布的項目不能再以改決定的方式撤銷正式版本；若要改回，基於目前正式版提出新建議。尚未發布的不採納項目之後仍可重新討論，但須重新比較目前基準並作新決定，保留原決定。

## 7. 部分採納發布與公開呈現

### 7.1 B 修改 5 點、A 採納 3 點的例子

| 項目 | 提出者 | 處理者 | 結果 | 正式內容 | 留存 |
|---|---|---|---|---|---|
| S001-01～03 | B | A | 採納 | 合併至 v1.1 | 原文、建議、決定、操作者、時間、v1.1 關聯 |
| S001-04～05 | B | A | 不採納 | 維持原文 | 同樣完整保留，沒有合併版本 |

發布確認畫面明示「採納 3 項、不採納 2 項、待討論 0 項」，列出本次真正要套用的項目與新版預覽。按「確認並發布」成功後，只將那 3 項套入 v1.0，生成 v1.1。

如另有待討論項目，可以先發布已採納且無衝突的項目；確認畫面需明示未處理項目仍留存、未進入本次發布。剩餘項目之後發布必須重新對照新正式版，不能重複套用已發布項目。

全部不採納、全部待討論，或採納後正文與目前版完全相同：不產生空的新版本。決定及完成／待討論狀態仍保存。

### 7.2 正式版本與建議記錄分開

正式正文、公開連結及正式 PDF 只含已發布內容。正式版本卡仍只顯示版本名、修改／新增／刪除統計與實際內容變更說明。版本卡不加基準、權限、操作者、時間或拒絕項目全文。

有協作檢視權限的人另見「建議記錄」入口及處理摘要：

> 修訂建議 S001：B 提出 5 項修改；A 採納 3 項、不採納 2 項。已採納內容併入 v1.1。查看完整記錄。

完整記錄中，不採納項目仍顯示修改前後文字、A 的決定與選填說明。發布關聯會保留於協作資料；公開版本資料不包含未發布建議內容或私下討論。

### 7.3 AI 摘要

送出建議時可另有「修訂建議摘要」，描述 B 提出什麼；是否自動生成依摘要服務是否實際啟用，不作本功能啟用的先決條件。

正式版本 aiSummary 只比較新正式版與緊接前版，描述實際採納後的變更，不將不採納／待討論內容寫成已生效。採納結果與歷程由系統記錄，不依 AI 推測；AI 沒有採納、授權或發布權。

Codex 直接產生正式版本仍遵守既有 aiSummary 發布規則。線上發布是否自動補摘要必須按實際部署狀態顯示，不能因這份規格便宣稱已啟用。

## 8. 完整歷程與可追溯範圍

每個操作事件包括：不可重用的事件 ID、documentId、suggestionId／itemId、操作者穩定 ID、當時名字／公司快照、伺服器時間、操作、前後狀態、說明、基準版號／hash、關聯發布 ID／正式版號（適用時）。前後文字保存在原始建議快照並以識別碼關聯；記錄不存 token、密碼或服務金鑰。

至少留存：送出、留言、採納、不採納、改決定、撤回、調整後再提出、重新比較、發布受理／成功／失敗，以及權限開關／連結停用／主控者變更。

歷程採追加式紀錄，介面不提供抹除已送出項目或已存在事件的硬刪除。未採納、撤回或被取代項目仍可追溯。封存文件保留建議及歷程；連結停用不刪提出者資訊。

本版記錄證明系統內的具名操作及文件變更，沒有電子簽章、真人身分驗證或法律簽署功能。

## 9. 介面流程

### 正式文件頁

維持現有 Word 類型正文與右側修訂檢視。啟用模式後，原「完成修訂-版本更新」換為「送出修訂建議」。送出成功顯示建議編號，正式版本選單保持原版號。草稿不自動丟棄；成功保存確認後才清除該份已送出草稿暫存。

「修訂建議」區列出編號、提出者、基於哪版、狀態、採納／不採納／待討論數量。正式版本選單只列正式版；建議清單另列，避免把建議誤認為已生效版本。

### 建議檢視

左側是原文與建議內容的 Word 式標記；右側為具名項目卡。每卡顯示修改前後內容及處理結果，點卡定位正文。有權限者見「採納」「不採納」「加入說明」；其他協作者可讀結果，無相應權限者不顯示操作按鈕。

「建議內容」「採納後預覽」切換必須明示是否正式內容；正式版本永遠唯讀。窄螢幕右欄移至下方，項目 ID／內容／決定仍完整可讀。介面標記有文字狀態，不只依賴顏色。

### 發布確認

顯示目前正式版、本次採納範圍、未採納及未決數量、預期新版、正文預覽。有發布權者按「確認並發布」。處理中阻止重複點擊；失敗保留選擇並提供重試；不先標「已發布」。沒有實際採納變更時不啟用發布。

## 10. 儲存、權限與發布一致性（設計約束）

現有 GitHub repo 與 Pages 是公開文件管線。本版建議：未發布建議、留言、權限與完整操作歷程由 Worker 授權後讀寫的私有持久儲存管理，不放入公開 document.json、靜態 HTML 或 public Git 歷史。只把已確認正式內容交給現有 GitHub／Pages／PDF 管線。這要求新協作資料儲存；本輪不選定或建立雲端產品、帳戶及費用。

用私有服務的一致性操作保存「決定＋事件」及「權限調整＋事件」，失敗時不能只改狀態卻缺記錄。服務端執行每個能力檢查；隱藏按鈕不是授權控制。

發布依文件序列化並有不可重用的 publicationId：

1. 在服務端受理時驗證目前權限、最新基準、項目決定與所選內容，凍結發布快照及 hash。
2. 受理與權限調整有明確先後次序；先被停權的操作不能受理。已受理的發布可完成，事後停權不追溯撤銷該次操作；畫面須能查到發布受理時間與操作者。
3. 原 `/versions` 在此模式下不能被一般編輯者繞過；正式附加版必須對應服務端受理的採納快照，不能接受客戶端提交任意正文。
4. GitHub 以當前文件 SHA 與 latestVersion 防止競爭覆蓋。若受理後他人先發布，轉為需重新比較，不強行附加。正式寫入成功才產生新版；記錄 publicationId 供重試核對。
5. 若 GitHub 成功但協作服務確認中斷，依 publicationId／內容 hash 找回同一正式版並完成記錄，不能再加第二版。正式版本一旦成立不可因服務確認失敗刪除。
6. Pages／PDF 尚未完成時分別顯示「正式版本已儲存，公開網址更新中」；儲存、部署成功及摘要完成為不同狀態。保留現有發布狀態與較舊產物防覆蓋設計，不宣稱背景功能已上線。

事件讀取權限與協作內容權限一致；公開讀者不取得私下修訂內容。權限／建議 API 使用原有連結 token 認證，前端不持有 GitHub／AI／儲存服務憑證。每份文件只能由其具管理權的人開關本文件能力，不可藉跨文件連結操作別份文件。

## 11. 衝突、並行與失敗

- A、C 同時對同一項作決定：以建議記錄版本校驗，只接受第一個符合目前狀態的操作；另一人見最新決定並可明確再次作決定。不得靜默最後寫入覆蓋。
- 發布預覽開啟後，其他人改決定：快照／決定版本不符，要求重新預覽，不能發布舊選擇。
- 建議基準落後：顯示需重新比較。第一階段不自動合併；保留原始項目，產生關聯的新版建議及新差異，相關範圍需重新決定。原採納不自動套到改過的文字。
- 跨建議重疊：先發布一份後，其他建議按新基準重新比較，不疊加過時快照。
- 權限變更不重載正在編輯的正文；拒絕操作時提供原因，保留未送出內容。恢復權限後可重新驗證再送出。
- 斷線／伺服器失敗：內容保持，操作未保存不能顯示成功；使用請求 ID 防重複送出、重複事件及重複版本。
- 不採納後重新提出：新建議關聯原項目，能查到原決定及新結果。

## 12. 第一階段範圍與方案取捨

採用本版建議：每人具名連結＋可調整能力＋修訂建議＋單項決定＋確認發布＋追加歷程。它銜接現有分享方式，足以處理兩家公司合作與部分採納。

不採用共用密碼作唯一權限來源：設定簡單，但不能滿足多人操作歸屬。先不導入完整帳號／雙方簽署：身分可更嚴格，但增加帳戶、登入與簽署需求，超出本輪目的。

第一階段不包含：共同即時編輯、強制雙人／雙公司核准、電子簽署、離線文件往返、自動發訊息、AI 自動採納、已公開文件轉為私密、歷史版本重編、舊修訂自動回填、產品程式實作或部署。

## 13. 驗收案例（供後續實作，未執行）

1. B 送出 5 項：正式版及公開 PDF 仍為 v1.0；建議清單有 S001 與完整原文／建議。
2. A 採納 3、不採納 2，發布：只增加一次 v1.1；正文只含 3 項；完整記錄仍有另外 2 項與 A 決定。
3. 採納 3、待討論 2 項先發布：剩餘保持未決、不算不採納，後續必須重新比較且不重複發布原 3 項。
4. 全部不採納或正文無異動：有處理記錄，正式版號不增加。
5. B 無採納／發布權：直接呼叫 API 仍被拒絕；具權限的其他人可以作決定與發布並留名。
6. 主控者開／關權限：同一舊分頁下一個操作按目前權限判斷；歷程有前後能力；不丟草稿。
7. 採納後改不採納：發布前依最新決定；原採納事件仍可查看。已發布項目只能以新建議修正。
8. 提出者連結停用／改名／文件封存：原姓名快照與建議歷程不消失。
9. 基準變動、同項並行決定、預覽後改決定：阻止過時套用／發布，保留原建議。
10. 重複送出／重複發布／GitHub 成功後服務中斷：同一請求只產生一份建議、一組事件或一個正式版，可恢復記錄。
11. 公開 HTML／PDF／repo 中沒有未發布建議、未採納文字、私下留言、權限 token 或金鑰；協作資料只透過授權讀取。
12. 正式卡保留「版本名＋引擎總統計＋實際變更說明」；建議採納數量不冒充引擎修改次數。
13. 正式摘要只描述最終採納內容；AI 不改權限、不作採納決定、不發布。
14. 桌面與窄螢幕都能定位每項、閱讀全文、辨識決定；部分採納預覽與真正發布內容一致。

## 14. 規格自檢與下一步

已自檢：用語統一；正式版與建議編號分開；權限可撤銷且留事件；決定與發布分開；未採納／未決不消失；部分採納及重複請求可追溯；私有協作資料與公開正式資料邊界明確。

需由使用者檢視的本版建議：具名連結優先、能力拆分、允許自己採納自己的建議、允許先發布已決部分、私有協作儲存，以及第一階段不自動合併落後基準。確認規格後才另整理實作計畫；本規格不是實作或部署授權。
